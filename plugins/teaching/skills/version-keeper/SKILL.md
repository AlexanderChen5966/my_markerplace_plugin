# version-keeper

## 設計前提：教師不使用 git

論文版沒有這個問題——論文素材唯讀、永不改版。

教學版的素材會改，所以需要版本保護。但**不能預期教師會用 git**：
他不會打指令、不會看 diff、不會處理衝突。要求他學 git 就等於這個機制不會運作。

所以改用**純檔案操作的影子資料夾**：零設定、零依賴、跨平台，教師連機制存在都不需要知道。

需要的其實只有兩件事：

1. 「我改壞了要能回去」 ← 本 skill 負責
2. 「這份是不是最新的」 ← `stale-check` 負責，不需要版本控制

---

## 使用方式

### 自動（主要用法，教師不需觸發）

任何 skill 要覆寫 `raw/living/` 或 `outputs/` 下的**既有**檔案前，自動呼叫本 skill 建快照。

### 手動（教師偶爾會用）

```
我改壞了，回到之前那版
這份教案上週的版本給我看
清理一下舊版本
```

---

## 快照規則

### 路徑對應

```
_versions/<原始相對路徑>/<檔名>.<YYYY-MM-DD-HHmm>.<副檔名>
```

範例：

| 原始檔 | 快照 |
|--------|------|
| `raw/living/MKT101-U03-講義.md` | `_versions/raw/living/MKT101-U03-講義.2026-08-03-1430.md` |
| `outputs/MKT101-2026F/lesson-plans/MKT101-U03.md` | `_versions/outputs/MKT101-2026F/lesson-plans/MKT101-U03.2026-08-03-1430.md` |

保留原始目錄結構，還原時路徑一目了然。

### 什麼要快照、什麼不要

| 目標 | 快照 | 原因 |
|------|:---:|------|
| `raw/living/` | ✅ | 教師手寫內容，改壞了寫不回來 |
| `outputs/**/*.md` | ✅ | 教案、投影片原稿、題庫 |
| `wiki/` | ✅ | AI 維護但含教師備註段落 |
| `raw/fixed/` | ❌ | 唯讀，不會被改 |
| `raw/converted/` | ❌ | 可從原檔重新生成 |
| `outputs/**/*.pptx` `*.pdf` `*.docx` | ❌ | 渲染產物，可從 .md 重新生成 |
| `_versions/` 自身 | ❌ | 不遞迴 |

**渲染產物不快照**是重要決定：pptx 是二進位、體積大、且完全可從 Markdown 重建。
快照它們只會讓 `_versions/` 爆掉。

### 首次寫入不快照

檔案不存在時直接寫入，沒有東西可快照。

## 保留策略

`_versions/` 會無限成長，所以需要自動清理。**每次建立快照後順手執行清理**，
不需要教師記得。

| 規則 | 保留 |
|------|------|
| 近期 | 每個原始檔最近 **10 個**快照 |
| 月度 | 每月**最後一個**快照，保留 **12 個月** |
| 學期封存 | 學期結束時，該學期最後一版移入 `archive/<term>/` |
| 其餘 | 刪除 |

範例：一份講義改了 40 次、跨 8 個月 → 最後保留 10（近期）+ 7（前 7 個月各一）= 17 個快照。

### 清理實作要點

```bash
# 對每個原始檔的快照群組：
# 1. 按時間戳排序
# 2. 保留最新 10 個
# 3. 剩下的按 YYYY-MM 分組，每組保留最新 1 個
# 4. 月度保留超過 12 個月的刪除
```

刪除前**不需要問教師**——這是自動維護，問了反而困擾。但清理量大時在回報中提一句。

## 還原

```
我改壞了，回到之前那版
```

執行：

```
raw/living/MKT101-U03-講義.md 的歷史版本：

  1. 2026-08-03 14:30（今天，最新的舊版）
  2. 2026-08-01 09:15
  3. 2026-07-28 16:42
  4. 2026-07-15 11:20（7 月月度版本）
  5. 2026-06-30 17:05（6 月月度版本）

要還原到哪一個？

（還原時我會先把現在這版也存成快照，所以你隨時能再回來。）
```

**還原前必須先快照當前版本。** 否則教師還原後發現拿錯版本，就真的救不回來了。

還原後提醒下游影響：

```
✓ 已還原到 2026-08-01 09:15 的版本
✓ 還原前的版本已存為 _versions/.../2026-08-03-1512.md

⚠️ 這會影響下游：ODEP 條目與教案的 source_hash 現在對不上了。
   要跑 stale-check 看看嗎？
```

## 顯示差異

```
這份教案上週的版本跟現在差在哪
```

用 `diff` 比對，但**輸出要翻譯成教師看得懂的話**，不要貼原始 diff：

```
跟 2026-08-01 那版比，你改了三個地方：

1. 活動時間從 20 分鐘改成 28 分鐘
2. 加了「失敗案例反推」的說明（第三個環節）
3. 刪掉原本第四個區隔變數的細講

（第 2、3 點是配套的——為了塞進案例活動，砍掉了變數細講。）
```

最後那句「為了 X 而砍掉 Y」是 AI 該做的加值：**看出改動之間的關聯**，不只列出差異。

## 排除規則

`_versions/` 必須被以下機制排除：

| 機制 | 排除方式 |
|------|---------|
| NotebookLM 上傳 | 白名單制，本來就不含 |
| `wiki/INDEX.md` | 不列入 |
| `stale-check` | 不掃描 |
| 全庫統計（`course-health-check`）| 不計入條目數 |
| Obsidian 搜尋 | 建議在 vault 設定加入排除（工程師一次性設定）|
| git（若有）| `.gitignore` 加 `_versions/` |

**Obsidian 排除是實務重點**：不排除的話教師搜尋「市場區隔」會跳出 20 個舊版，非常困擾。

---

## 與 Obsidian File Recovery 的關係

Obsidian 內建 File Recovery 核心外掛（預設開啟，自動存快照）。

兩者**並存互補**，不衝突：

| 機制 | 保護範圍 | 保留期 |
|------|---------|-------|
| Obsidian File Recovery | 只有在 Obsidian 內編輯的檔案 | 短（預設 7 天）|
| `_versions/`（本 skill）| 所有被 skill 寫入的檔案 | 長（近 10 版 + 12 個月）|

教師在 Obsidian 手動打字的改動由 File Recovery 接；AI 寫入的改動由 `_versions/` 接。
兩邊都有，才不會有缺口。

**選配第三層**：工程師若願意，可設 git auto-commit hook 或讓 vault 放在
iCloud／OneDrive（本身有 30 天版本史）。但 kit 不依賴這些。

---

## 不要做的事

- **不要快照渲染產物**（pptx/pdf/docx）
- **不要遞迴快照 `_versions/`**
- **不要在還原前跳過當前版本的快照**
- **不要把原始 diff 貼給教師看**
- **不要讓教師知道這個機制存在**。理想狀態是他從來不需要想起版本這件事，
  只在真的改壞時說一句「回到之前那版」就好
