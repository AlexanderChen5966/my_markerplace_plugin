## 1. 分類

8 個角色分成 5 類。分類的依據是**會不會碰公司資訊**與**主要產出是什麼**：

| 類別 | 角色 | 主要產出 | 公司資訊 |
|---|---|---|---|
| **開發** | App 工程師（`app-engineer`） | 程式、任務文件、MR | ✅ 載入 |
| | 網頁前端（`web-frontend`） | 程式、任務文件、MR | ✅ 載入 |
| **設計** | UI/UX 設計師（`uiux-designer`） | 畫面、圖、icon（Figma、程式碼、SVG／PNG、artifact）；公司畫面與個人作品、side project 都用 | 只在改公司畫面時 |
| **學術** | 教授做研究（`prof-research`） | 文獻、wiki 條目、論文素材 | ❌ 一律不載入 |
| | 教授備課（`prof-teaching`） | 教案、簡報、測驗、評分標準 | ❌ 一律不載入 |
| **創作** | 個人專案、創作與實驗（`maker`） | 遊戲、3D、像素圖、互動作品；Python／AI／RAG 等個人實驗與 side project | ❌ 一律不載入 |
| **經營** | 行銷策略（`marketing-strategist`） | 行銷計畫、內容、活動、文案 | 只在經營公司品牌時載入該品牌資料；slc 系統知識不載入 |
| | 創新創業（`venture-builder`） | 可行性判斷、市場利基、新事業與 side project 的決策 | ❌ 一律不載入 |

**不做成角色的**：後端工程師（2026-11-09 決定先不加，讀後端用開發類角色）。

## 2. 組成原則

```
角色 = 共同層 ＋ 功能包（1～2 個）＋ 角色自己的 MCP／連接器 ＋ 排除清單
```

1. **角色只寫「要什麼」，不寫指令或路徑**：怎麼載入交給轉接層（之後寫）
2. **共同層所有角色都有**；**公司包只能掛在開發類，以及 UI/UX 改公司畫面時**；行銷角色經營公司品牌時，只加該品牌的行銷資料
3. **排除清單優先於功能包**：同一個零件同時被包含與排除時，以排除為準
4. **三層記憶不屬於角色**：所有角色讀同一份記憶；記憶是「你」，角色是「工作方式」
5. **repo 自己的 `.claude/`（hook、ZeroSpec、Matt 大型工作組）不放進角色**：留在 repo，進那個資料夾自然生效
6. **ID 一律 ASCII**（`app-engineer`），中文名放 `display_name`：換作業系統時路徑與編碼不出問題

**反問規則（草案）**

1. **先問再答**：你提出想法時，先問最會改變結論的問題，不要直接給可行性判斷或做法清單
2. **一輪最多 3 題**：每題寫出為什麼要問，以及它目前的猜測，你可以只回「對」或改正
3. **查得到的自己查**：競品、價格、市場規模先查；只問你才知道的事（目標、資源、底線、你對客戶的第一手了解）
4. **整段對話都反問**：你的回答有矛盾、數字太樂觀、或把希望當事實時，當下提出來，不等到最後
5. **可以不同意**：覺得不該做就直接說理由，不為了鼓勵而附和；被你說服要講清楚是哪個理由
6. **答不出來也算結果**：寫進一頁決策的「還不知道的事」，當成下一步要驗證的項目
7. **要停得下來**：問到能下結論就給結論；你說「先給我看法」時，就用目前的假設回答並標明假設

**常用的反問**

| 面向 | 問題 |
|---|---|
| 對象 | 具體是誰會用？你認識這樣的人嗎？ |
| 痛點 | 他們現在怎麼解決？花多少錢或時間？最近一次抱怨是什麼時候？ |
| 利基 | 為什麼現有的做法沒解決？為什麼是現在？ |
| 你 | 為什麼是你來做？你有什麼別人沒有的資源或經驗？ |
| 資源 | 每週能投入幾小時？最多願意賠多少錢、撐多久？ |
| 動機 | 這是要賺錢、要練技術，還是做好玩？三者的判斷標準不同 |
| 驗證 | 這週能做什麼事，讓真人用行動告訴你要或不要？ |
| 退場 | 看到什麼結果你會放棄？ |

**一頁決策的格式（草案）**

| 欄位 | 內容 |
|---|---|
| 要解決誰的什麼問題 | 一句話，對象要具體 |
| 利基點 | 現有做法留下的缺口，附競品來源 |
| 證據 | 查到的事實與連結；模擬或推測另外標示 |
| 最可能失敗的原因 | 最多三個 |
| 粗略數字 | 要賺錢才填：價格、成本、損益平衡；side project 改填要花的時間 |
| 決定 | 做／不做／先小測試 |
| 還不知道的事 | 反問時答不出來的項目 |
| 最便宜的真實測試 | 一週內能做、會得到真人反應的事 |
| 交給誰 | 下一步由哪個角色接手 |

## 5. UI/UX 角色的「去 AI 味」檢查清單（初稿）

網頁畫面先跑 `npx impeccable detect`，這份清單補它涵蓋不到的部分（中文文案、icon 規格、和既有畫面的一致性）。Flutter 畫面掃描器不適用，整份人工對照。完成後用 Claude in Chrome 截圖逐條看，任何一條成立就要改，或寫明為什麼保留：這些痕跡代表「沒有經過選擇的預設值」，案子明確要這個風格時可以留。

**開始前**
- [ ] 有這個作品或專案的 `DESIGN.md`；個人作品、side project 還沒有的話，先定色彩、字型、間距、icon 規格，再開始畫

**視覺**
- [ ] 顏色、字型、圓角、陰影全部來自該專案的 `DESIGN.md` token，沒有模型預設值
- [ ] 沒有紫藍或粉紫的漸層背景、漸層文字
- [ ] 沒有用 emoji 當圖示；圖示來自專案既有的圖示庫
- [ ] 不是每個區塊都包成「白卡＋圓角＋陰影」
- [ ] 沒有「置中大標題＋副標＋兩顆按鈕＋三欄功能卡」的固定首頁版型
- [ ] 間距有節奏（相關的近、不相關的遠），不是全部等距
- [ ] 資訊密度符合使用情境（後台表格要密，不是行銷頁的大留白）

**第二層 AI 味（模型避開紫色漸層之後的新預設，看起來有品味，更難發現）**
- [ ] 不是奶油色底加赤陶色點綴
- [ ] 不是細襯線大標題配一個斜體或換色的強調字
- [ ] 不是近黑底只配一個螢光綠或朱紅
- [ ] 沒有報紙式細線密排版面
- [ ] 沒有全大寫或等寬字體的裝飾小標籤
- [ ] 01／02／03 編號只用在真的有順序的內容
- [ ] 沒有假視窗三圓點

**真實性**
- [ ] 沒有捏造的數字、客戶 logo、推薦語；沒有資料就標示待補

**文案**
- [ ] 沒有空泛形容詞（「強大的」「無縫的」「一站式」「賦能」）
- [ ] 按鈕寫動作（「匯出報表」），不寫「立即開始」「探索更多」
- [ ] 中文用台灣用語，沒有翻譯腔；可借 teaching 工具包 humanize-zh 的觀念
- [ ] 狀態訊息具體（「已匯出 128 筆」），不寫「操作成功！」

**一致性**
- [ ] 新畫面和同專案既有畫面放在一起，看不出是另一個人做的
- [ ] 元件用專案既有的（例：b2b-manager 的 `NegativeButton`、`PositiveButton`），沒有另做一套

**Icon（做 icon 時加看這組）**
- [ ] 同一組 icon 用同一個網格尺寸（例：24×24）、同一個筆畫粗細、同一種端點與轉角
- [ ] 風格統一：線框或填色擇一，不混用；不用 3D 漸層、玻璃質感這類 AI 常見效果
- [ ] 在實際尺寸（16、24、32 px）看得清楚，不靠放大才看得懂
- [ ] 隱喻直接（垃圾桶＝刪除），不為了「有設計感」改成抽象圖形
- [ ] 輸出格式符合用途：網頁用 SVG；App 依平台規格輸出各尺寸 PNG

> 這份清單之後可以做成 `anti-ai-look` 規則檔或小 skill；要先在一兩次實際改畫面或做 icon 時試用，再決定形式。第二層來自 avoid-ai-design 與 Impeccable 的 README。
