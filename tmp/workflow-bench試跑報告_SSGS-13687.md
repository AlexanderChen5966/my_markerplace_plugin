## 3. 這次試跑發現的問題（正式跑之前要修）

1. **這張卡分不出高下**：v1 已經 14/14，v2 的價值只出現在審查深度和 MR 格式，準確度量不出差異。正式比對需要更難的卡：需求有歧義（測 grilling）、根因不明顯（測 diagnosing-bugs）、容易漏做（測 spec 審查）。
2. **權限白名單太窄**：拒絕的大多是 `cd … &&` 開頭的複合指令、`for` 迴圈、`flutter --version`、`git check-ignore`、輸出重新導向、`git apply -R`（v1 想暫時還原修正驗證測試）、`flutter build web`。兩邊條件相同，但會逼 agent 繞路、多花回合。正式跑要放寬，而且**放寬後 v1 也要重跑**，條件才一致。
3. **只跑 1 次**：沒有穩定度資料。正式跑每版至少 3 次。
4. 已修正：transcript 會重複記同一個 tool_use，分析腳本原本把叫用次數算成 2 倍（已改成依 id 去重）。
5. Jira MCP 當時連不上，題目改用任務文件的「使用者回報」段。

## 4. 初步結論

- 在根因清楚的 bug 上，v2 **準確度和 v1 相同**，**費用多 18%**。多出來的錢主要花在 spec subagent，換到的是更深的審查（3 個測試弱點、1 個文件歧義）和格式固定的 MR 說明。
- v2 的條件觸發看起來是對的：不該觸發的 grilling 沒觸發。但 diagnosing-bugs 和 tdd 在這種「流程已指定」的 prompt 下不會自己觸發，要等難一點的卡才看得出它們有沒有作用。
- 只有 1 張卡、1 次，不足以下結論。

## 5. 決定（2026-11-09）

基於成本考量：**這次試跑就是 v1、v2 的正式基準**；之後 v3、v4 也只用 SSGS-13687 跑一次比對。
白名單、prompt、模型維持現狀，不放寬（改了 v1、v2 就要重跑）。

第 3 節的 1～3 點因此不處理，只記錄為限制：
- 準確度可能都會滿分，比不出差異
- 沒有穩定度資料
- 權限拒絕會讓 agent 繞路

比較重點改看：費用、token、回合數、開發模組觸發是否正確、審查找到的問題、權限拒絕次數。

> 若之後要驗證 grilling、diagnosing-bugs 的實際效果，候選卡留著：SSGS-13504（做法不只一種）、SSGS-12729（後端 enum P0）、SSGS-12681（UI 對照組）。
